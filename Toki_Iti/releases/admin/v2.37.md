## Highlights

### Introducing OAuth 2.1 Support — End-to-End, From Day One

This release marks the **debut of full OAuth support** across the platform — both the server-side engine, built to match the **OAuth 2.1 specification**, and the brand-new admin portal UI that lets you actually see and control it. This isn't a UI layer bolted onto a mature backend — OAuth is new from the ground up, and this release brings it to life with a complete, usable interface from day one.

## Why We Built This

Rolling out OAuth support isn't just about ticking a spec-compliance box — it's about giving your organization a secure, standards-based way to let applications connect on behalf of agents and contacts. But a new OAuth engine without visibility tools is risky to operate: admins need to know *who* has access, *what* they can do with it, and *how* to shut it off if something goes wrong.

That's why, alongside the new OAuth engine, we built a full management UI so the feature is trustworthy and governable from its very first release:

- **App Registration UI** — Master admins can manage an organization application's secret, and agents get their own registration UI to set up and manage a personal secret — no shared, less-secure credentials required.
- **OAuth Settings** — New global controls let admins:
  - Enforce **client secret authentication** at the global level, even for applications registered as "public" — closing the loophole where none-secret token exchanges could otherwise slip through.
  - Set **consent mode** independently for the TECH portal (agents) and client portal (contacts), deciding whether individuals can self-serve consent or whether that decision stays centralized with admins.
- **Consent & Session Management UI** — Master admins get a full view of every consent grant and authorized session across the org, with the power to revoke a session, revoke a grant, or issue new consent — at the individual, account, or org-wide level. Agents and contacts get a mirrored self-service experience for managing their *own* connections.
- **Personal Secrets** — For MCP connector scenarios where an application is registered via OpenAPI (often set up by the customer, not us), sharing a single secret across every user is a security risk. Now, individual users can generate and use their **own personal secret** when granting consent — meaning every application can be treated as confidential, not public, right out of the gate.

## What This Means for You

✨ **Security teams** get full visibility from launch day — no black-box period where OAuth exists but can't be audited.

✨ **Admins** can set org-wide OAuth policy (secrets required, consent centralized) before OAuth usage even scales up.

✨ **Agents and contacts** get self-service confidence from the start — they can see exactly what they've authorized and revoke it themselves.

✨ **Every integration is safer by default**, thanks to personal secrets eliminating shared-credential risk for connector-based OAuth setups.

## Bottom Line

We didn't just add OAuth — we launched it **fully formed**: spec-compliant on the server, and fully visible and controllable in the UI. Secure, delegated access is now a first-class citizen of the platform, manageable by everyone from master admins down to individual agents and contacts. 🚀
